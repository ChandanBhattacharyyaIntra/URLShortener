1. Problem statement

The interview assignment is not “write a URL shortener.” It is to build a working prototype that turns a requirement into a reviewable engineering outcome using an agentic execution model. The product scenario is a URL shortener with core APIs, analytics, and reliability. The evaluation weight sits on orchestration quality, architecture, decomposition, validation, and engineering judgment.

Principle from the PDF: agents execute under defined autonomy boundaries; humans own oversight, approvals, and final quality.

Required capabilities:

  • Requirement understanding (including ambiguous input)
  • Task decomposition with dependencies and sequencing
  • Brownfield codebase reasoning (impacted modules and data flows)
  • Workflow orchestration that is not a linear task list: DAG, gates, parallel/sync, lineage, human checkpoints, retries, fallback/rollback, safe-stop, policy guardrails, audit, reliability metrics, dynamic replan
  • Production-quality code, tests, and documentation
  • A final engineering summary of plan, artifacts, risks, assumptions, and limits

Deliverables: runnable prototype, architecture overview, three scenarios (greenfield, brownfield, ambiguous), setup, testing approach, limitations, and trade-offs.

2. How this prototype solves that problem

The system is split into two planes that share one ASP.NET Core host so a reviewer can run everything with dotnet run:

Data plane — engineering output

A real URL shortener: create, redirect, analytics, expiration, custom aliases, deactivate, validation, rate limits, health/metrics. This proves the “working prototype” and “production-quality APIs” parts of the rubric.

Control plane — agentic SDLC

An orchestrator that executes a dependency graph of SDLC stages with entry/exit gates, parallel build paths, sync joins, human approvals, retries, rollback, safe-stop, policy checks, audit events, and reliability metrics. This is the critical differentiator.

Stage workers are deterministic (no LLM API key required) behind a single StageAgents.Run(node, context, prior) interface. That is intentional: the assignment grades governance and orchestration, not vendor-chat wrapping. An LLM can be plugged into the same interface later without rewriting the DAG, gates, or audit model.

4. Data plane — URL shortener

Redirect is the hot path and is fail-closed:

  1. Look up code (404 if missing or reserved).
  2. If inactive or past expiresAt → 410 Gone (do not redirect).
  3. Increment clicks, append a ClickEvent (referrer + user-agent).
  4. Return 302 to the original URL (temporary redirect so analytics keep working if the target changes later).

Reliability and safety controls

  • URL allow-list: only http/https; block javascript:, data:, file:, vbscript:.
  • Alias rules: 3–32 chars, alphanumeric / _ / -; reserved words (api, health, …) rejected.
  • Collision handling: random 7-char base62 codes, max 5 retries, then 503.
  • Rate limit: in-process token bucket (stricter on writes).
  • Headers: X-Content-Type-Options, X-Frame-Options, Referrer-Policy.
  • Persistence: JSON snapshot with temp-file + atomic replace (no native SQL driver on the interview laptop).

5. Control plane — agentic orchestrator

This is not a sequential script. Ready nodes whose dependencies are satisfied run together. Waves look like:

requirements ↓ architecture ⚑ human gate (change control) ↓ ┌─────────────┴─────────────┐ │ implementation │ parallel group “build” │ test_planning │ └─────────────┬─────────────┘ ↓ sync join ┌─────────────┴─────────────┐ │ testing (needs both) │ parallel group “verify” │ documentation (needs impl)│ └─────────────┬─────────────┘ ↓ release ⚑ human gate (quality / go-no-go)

Each node records:

  • entry gate before work
  • bounded retries with backoff
  • policy evaluation on artifacts
  • exit gate after success
  • decisions (lineage) and named artifacts (spec, ADR, evidence, test plan, checklist)
  • optional snapshot for rollback if a later attempt fails

Controlled autonomy: implementation, test planning, testing, and documentation run as agents. Architecture and release wait for a human when approvalMode=manual. auto is only for unattended tests/demos and is itself written into lineage so it is never a silent bypass.

Safe-stop sets a cooperative flag and completes a pending approval as denied so the engine cannot hang on a human gate. Replan records that upstream output changed and resets unfinished nodes.

6. Three required scenarios

ScenarioRequirement inputWhat the run demonstrates
greenfield Build a shortener from scratch with APIs, analytics, expiration, aliases, reliability. Full SDLC decomposition from a clear spec; implementation evidence against that spec.
brownfield Service already in use; add deactivate without breaking analytics; 410 fail-closed. Impacted modules, change-control approval before architecture, compatibility of redirect vs disable.
ambiguous “Something like bit.ly. Make URLs better. Ship soon.” Ambiguities listed (auth, SLA, alias policy, analytics TTL); explicit assumptions; MVP envelope (no SSO, JSON store, rate limits).

The ambiguous scenario does not invent hidden requirements. It records assumptions and proceeds only inside that envelope — that is the validation/risk-control behavior the rubric asks for.

7. How to run

Prerequisites: .NET 8 SDK and Visual Studio 2022 (17.8+) or the dotnet CLI. global.json pins SDK 8.x so Visual Studio does not try to target .NET 9.

dotnet test
dotnet run --project src/UrlShortener.Api

Then open http://localhost:5169 for the dashboard, or call the APIs below (PowerShell examples use port 5169 from launchSettings.json).

8. URL shortener API

JSON uses camelCase. Errors return { "error": "message" } with the HTTP status below.

POST /api/urls — create

Body:

{
  "url": "https://example.com/campaign",
  "customAlias": "q4-promo",
  "expiresInSeconds": 86400,
  "createdBy": "dashboard"
}

customAlias and expiresInSeconds are optional. Success: 201 Created.

Invoke-RestMethod -Method Post -Uri http://localhost:5169/api/urls `
  -ContentType application/json `
  -Body '{"url":"https://example.com/campaign","customAlias":"q4-promo"}'
StatusWhen
201Created; response includes code and shortUrl
400Missing/invalid URL, bad alias, bad expiry, blocked scheme
409Custom alias already taken
429Rate limit
503Could not allocate a unique random code

GET /{code} — redirect

302 to the original URL and records a click. Use a client that does not follow redirects if you want to inspect the Location header.

curl -i http://localhost:5169/q4-promo
StatusWhen
302Active, unexpired link
404Unknown or reserved code
410Disabled or expired (fail-closed; no redirect)

GET /api/urls — list

Invoke-RestMethod http://localhost:5169/api/urls

Returns { "items": [ ... ] } newest first.

GET /api/urls/{code} — metadata

Code, original URL, timestamps, click count, active flag. Does not increment clicks (unlike GET /{code}).

GET /api/urls/{code}/analytics

Aggregates: total clicks, clicks by day, top referrers, last access, expiry, active flag.

Invoke-RestMethod http://localhost:5169/api/urls/q4-promo/analytics

POST /api/urls/{code}/deactivate

Sets active=false. Subsequent redirects return 410. Historical click events are kept (brownfield compatibility).

Invoke-RestMethod -Method Post -Uri http://localhost:5169/api/urls/q4-promo/deactivate

GET /health and GET /metrics

Liveness (status, uptime) and counters (url count, active count, total clicks). Suitable for a load-balancer probe in a later production hardening pass.

9. Orchestrator API

GET /api/orchestrator/graph

Static DAG: node ids, dependencies, approval flags, parallel groups, gates, retry policy, plus topological layers. Use this to visualize the workflow without starting a run.

POST /api/orchestrator/runs — start a scenario

{
  "scenario": "greenfield",
  "approvalMode": "auto"
}

scenario: greenfield | brownfield | ambiguous. approvalMode: auto | manual.

  • auto waits until the run settles and returns 201 with the full run (lineage, artifacts, metrics, events).
  • manual returns 202 immediately; poll GET until status is awaiting_approval, then approve.
Invoke-RestMethod -Method Post -Uri http://localhost:5169/api/orchestrator/runs `
  -ContentType application/json `
  -Body '{"scenario":"ambiguous","approvalMode":"auto"}'

GET /api/orchestrator/runs and GET .../runs/{id}

List or fetch one run. Important fields:

  • status — running | awaiting_approval | succeeded | failed | stopped
  • nodes — per-stage status, attempts, errors
  • lineage — decisions (who decided what and why)
  • artifacts — spec, ADR, evidence, test plan, docs index, release checklist
  • events — audit: gates, parallel waves, retries, approvals
  • metrics — successRate, retryCount, rollbackCount, mttrMs, endToEndLatencyMs
  • pendingApproval — node id + reason when blocked on a human

POST /api/orchestrator/runs/{id}/approve

{ "approved": true, "note": "ADR accepted; schema freeze" }

409 if nothing is waiting. Use approved: false to fail the gated node (and therefore the run).

POST /api/orchestrator/runs/{id}/stop

Cooperative safe-stop. Unfinished nodes become stopped.

POST /api/orchestrator/runs/{id}/replan

{ "reason": "Product owner changed analytics retention" }

Records lineage that upstream output changed and resets unfinished nodes. Intended to show governance when requirements move mid-run.

10. Best practices used

Design

  • Clear bounded context split (shortener vs orchestrator).
  • Domain logic in a service, not in HTTP handlers.
  • Immutable records for URL/click snapshots; updates via with.
  • Fail closed on security and expiry (410, not a best-effort redirect).
  • DAG as data, not hardcoded if chains — sequencing is inspectable.

API & HTTP

  • Correct status codes: 201, 302, 400, 404, 409, 410, 429, 503.
  • Create vs resolve vs inspect are different verbs/paths so analytics are not polluted by metadata reads.
  • Temporary 302 rather than 301 so caches do not pin a target forever.
  • Consistent error envelope { error }.

Security & change control

  • Scheme allow-list against open redirects / XSS-style payloads.
  • Rate limiting on writes.
  • Baseline security headers.
  • Human gates on high-impact stages (architecture, release).
  • Policy scan so artifacts cannot casually contain secrets.

Reliability & testability

  • Bounded collision retries; no infinite allocate loops.
  • Atomic file persist.
  • Isolated temp store in WebApplicationFactory tests.
  • Nine automated tests covering happy path, negative path, and all three orchestrator scenarios.
  • Health/metrics as the start of operability.

SDLC best practice in the orchestrator itself: test planning is parallel to implementation, then testing joins both. That matches real teams (QA does not wait for every line of code) and is the “parallel paths with synchronization” the assignment called out.

12. Suggested reviewer walkthrough

  1. Open this file plus docs/ENGINEERING_SUMMARY.md for plan, assumptions, and limits.
  2. dotnet test — expect 9 passing tests.
  3. Run the API; open the dashboard at /.
  4. Create a link, open /{code}, then inspect /api/urls/{code}/analytics.
  5. Deactivate the same code; confirm 410.
  6. POST orchestrator run greenfield / auto; confirm seven succeeded nodes, gate events, and metrics.
  7. POST brownfield; read the ADR artifact’s impacted modules.
  8. POST ambiguous; read ambiguities and assumptions on the requirements artifact.
  9. Optional: approvalMode=manual, approve architecture, then approve release — that is the human-in-the-loop story.

That path covers the PDF’s deliverables: a runnable prototype, architecture, three scenarios, setup, testing, and defensible trade-offs — with agents executing work and humans remaining accountable for high-impact decisions.
